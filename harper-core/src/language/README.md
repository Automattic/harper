# Harper Language Support Architecture

Compile-time plugin architecture. Each language implements the `LanguageModule`
trait and is wired in by the build system.

Working on this as an agent? Read [`AGENTS.md`](./AGENTS.md) in this directory.

## Architecture

- **`LanguageModule` trait** (`module.rs`) — the interface every language implements.
- **Build system** — `build.rs`/`build_lib/` discovers languages via `config.toml`
  and generates the integration code.
- **Feature flags** — optional languages are gated with `#[cfg(feature = "...")]`.
- **Morphology** (`morphology.rs`) — case/gender/number/mood shared by the
  non-English modules. `dict_word_metadata.rs` holds a single feature-gated
  `morphology` field and nothing else language-specific.

### Generated files — do not edit by hand

`mod.rs`, `languages.rs` and `registry.rs` are written by `build.rs` into this
directory. The wasm-facing `Dialect` enum is generated by `harper-wasm/build.rs`
into its `OUT_DIR` and is not committed. To change their contents, edit
`harper-core/build_lib/language_modules.rs`.

## Feature flags

```toml
# harper-core/Cargo.toml
language-module = []                        # internal marker; English always included
multilingual    = ["de", "pt", "sk", "pl"]
de = ["language-module"]                    # likewise pt, sk, pl
all-languages   = ["multilingual"]
```

With **no** language feature enabled, `pub mod language` does not exist and
English uses its original implementation — this is what keeps merges from master
clean. Every consumer crate (`harper-cli`, `harper-ls`, `harper-wasm`,
`harper-desktop`) enables `language-module` in its **base** `harper-core`
dependency, so the English module is always present; per-language features add
languages on top.

`just check-language-features` validates that the features agree across all
manifests.

## Configuration

Each language needs `harper-core/src/language/<lang>/config.toml`:

```toml
[language]
name = "German"     # omit `feature` for English -- always included
feature = "de"

[metadata]
confidence = 0.95   # detector ordering only, highest first

[[dialects]]
name = "Standard"
aliases = ["de", "german", "deutsch", "de-de", "de_de"]

[weir]               # optional
rules_subdirectory = "de"
```

The parser reads `name`/`feature` from `[language]`, `confidence` from
`[metadata]`, and `aliases` from each `[[dialects]]` entry. English's detector
confidence is hardcoded to `0.30` in the generator regardless of its config.

## Required files

```
harper-core/src/language/<lang>/
├── config.toml          # language metadata
├── module.rs            # LanguageModule implementation
├── dialects.rs
├── language_detection.rs
├── lexing.rs
├── mod.rs
├── parsers/
├── spell/
├── linting/
├── dictionary.dict      # base words with property flags
├── annotations.json     # affix rules + flag -> metadata mapping
└── test_sources/        # example texts, *.md or *.txt
```

Files are embedded with `include_str!()`, so the structure must match exactly.

## Adding a new language

1. Create `harper-core/src/language/<lang>/` with the files above.
2. Implement `LanguageModule` in `module.rs`.
3. `harper-core/Cargo.toml`: add `<lang> = ["language-module"]` and add `<lang>`
   to `multilingual`.
4. Forward the feature in `harper-ls`, `harper-cli`, `harper-wasm` and
   `harper-desktop/src-tauri` `Cargo.toml`.
5. Optional: add `stats.rs` and a dispatch arm in `harper-cli/src/bin/lang_stats.rs`.

Steps 3–5 are the only manual wiring; everything else is discovered from
`config.toml`. In particular `harper-wasm` needs no edit — its `Dialect` enum,
dialect imports and `From<Dialect> for Language` conversion (including the
`#[cfg(not(...))]` fallbacks to English for languages left out of a build) are
all generated by `harper-wasm/build.rs`.

Feature forwarding stays manual on purpose — different binaries ship different
language sets (CLI with everything, Chrome extension with English only), so each
consumer declares what it wants. `just check-language-features` verifies they
agree.

## Tooling

All development recipes are in `harper-core/src/language/justfile` and are listed
by:

```bash
just --list | grep language-
```

They cover spell-checking arbitrary text, inspecting word metadata, dictionary
validation and statistics, coverage and affix-efficiency analysis, Hunspell
comparison, test-template generation, and running the per-language test suites.
Each recipe documents its own usage; the justfile is the source of truth rather
than this README.

Two notes that the recipe help cannot express:

- **English is a special case.** Its dictionary lives at `harper-core/` rather
  than under `language/`, so some recipes do not apply to it.
- **Coverage needs a reference dictionary.** `just language-coverage <lang>`
  compares against `<lang>_dictionary.dict.gz` in the language directory. Only
  German currently ships one; other languages are skipped.

`just check-languages` runs the whole language suite — feature consistency,
per-language tests and the German coverage gate — and is called from
`just check-rust`, so it also runs in CI.

## Improving a dictionary

1. Add or correct entries in `dictionary.dict`.
2. Add any new property or affix flags to `annotations.json`.
3. Check the result with `just language-meta <lang> "<word>"` or
   `just language-meta-text <lang> "<sentence>"`.
4. Compare against Hunspell to find gaps: `just language-hunspell <lang> "<text>"`.
5. Confirm coverage has not regressed: `just language-coverage <lang>`.

**Flag characters are scarce and overloaded.** In German, 21 letters are
simultaneously a property *and* an affix rule, so a letter flag can generate
unintended surface forms. Only digits and punctuation are free — use digits for
new property flags.

Prefer dictionary data over Rust constants: a word list in a `const &[&str]` is
almost always misplaced. See `german/README.md` for the exceptions and why they
are exceptions.
